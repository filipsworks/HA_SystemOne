HA_SystemOne — jak polskie polecenie staje się akcją w Home Assistant

Wyszukiwanie po znaczeniu + klasyfikator TypeSafe: program wybiera tylko spośród istniejących urządzeń i akcji albo dopytuje — niczego nie zmyśla.

rest_command POST /decide
token Bearer z secrets.yaml
REST API Home Assistant wykonanie akcji:
/api/services/<domena>/<usługa> stan i lista urządzeń: /api/states
Kontener Docker: decide serve (port 8765)
obraz :cpu (~1 s / polecenie) lub :cuda (~0,3 s) · modele ładowane raz przy starcie
1
Katalog urządzeń urządzenia i dozwolone akcje (z supported_features),
polskie nazwy, aliasy, pomieszczenia i opisy z aliases.yaml
2
Wyszukiwanie po znaczeniu embeddingi bge-m3 + ChromaDB → 30 kandydatów (urządzenie, akcja)
radzi sobie z odmianą: „zgaś kuchnię”, „lampę w sypialni”
3
Reranker cross-encoder bge-reranker-v2-m3 → 5 najlepszych kandydatów
4
Decyzja: TypeSafe AI wybór jednego z 5 kandydatów albo „żaden”, z pewnością 0–1
+ sprawdzenie, czy to w ogóle polecenie dla domu
5
Bramka bezpieczeństwa pewność ≥ 0,8 i wybór inny niż „żaden” → wykonaj lub odczytaj stan niepewność → „Czy chodziło o: …?” · nic nie pasuje → „Nie mam urządzenia…” tylko usługi z listy dozwolonych — bez zamków, alarmów, bram i rolet
/config — pliki Twojego domu .env — adres HA, tokeny, klucz aliases.yaml — polskie nazwy eval/ — własny test dokładności data/ — katalog i indeks
/models modele z Hugging Face (~4,5 GB),
pobierane przy pierwszym starcie
TypeSafe API (chmura) skalibrowany klasyfikator:
wybiera z podanych opcji, nie generuje tekstu
Przygotowanie (raz i po zmianach) decide init → szkielet aliases.yaml decide sync → katalog z HA decide index → indeks decide eval → test dokładności
